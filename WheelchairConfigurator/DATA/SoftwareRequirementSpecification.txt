1. Introduction
1.1 Purpose
This Software Requirements Specification, hereinafter referred to as SRS, is a technical document defining the functional and non-functional requirements for the specified system. It serves as the primary technical foundation for development, verification (testing), and subsequent acceptance of the work, ensuring alignment between technical implementation and stakeholder expectations.
The goal of this SRS is to describe the design and implementation of an intelligent configurator for electric wheelchairs. The software automates technical checks, visualizes the assembly, and generates production documentation to eliminate prescription errors.
This document is intended for the CMonkey Ltd. development team, collaborating students from FZS and FDU, and the contracting authority as a basis for final software acceptance.

1.4 Product Scope
E-VozíkBuilder is a specialized Android platform system designed to manage and automate the configuration of individualized electric wheelchairs. The application replaces the traditional method of manually browsing through extensive physical catalogs. The system acts as a technical assistant providing:
* Clinical Assessment Mode: Therapists perform patient assessments via a diagnostic checklist. Based on input, the system recommends an assembly. Manual overrides are allowed but enforced by a real-time validation engine.
* Catalog Management Mode: Administrators manage the component database and update compatibility rules.
Through integration with a native rendering pipeline, the system ensures consistent visual representation and data hand-off to external manufacturing systems via PDF specifications.

2. Overall Description
2.1 Product Perspective
E-VozíkBuilder transitions manual wheelchair configuration into a unified digital environment where validation is handled automatically. Architecturally, the solution consists of four primary functional blocks:
* Presentation Core: Touch-first UI optimized specifically for 10"+ Android tablets.
* Validation Engine: A deterministic logic core (Rule Engine) enforcing technical, electrical, and ergonomic parameters defined in external datasets.
* Graphics Module: A native component leveraging hardware acceleration for off-screen image processing.
* Data Storage: A local-first persistence layer using an encrypted database for catalog data, rules, and local patient assessments.
The application functions as a standalone system (Offline-First) to ensure reliability in clinical settings without mandatory cloud connectivity.


2.2 Product Features/Functions
* Patient Intake: Structured form for ergonomic and environmental requirements.
* Component Selection: Filterable catalog with real-time validation of compatibility.
* Safety Logic: Enforcement of mechanical, electrical, and weight limits.
* Visualizer: Rendering of assembled configurations using 3D assets (where available).
* Export: Automated generation of technical Bill of Materials (BOM).


2.3 User Classes and Characteristics
* Therapist (Clinical User): A medical professional who translates clinical findings into technical configurations. Uses the assessment checklist and verifies the final visual assembly to ensure safety and ergonomic compliance.
* Supplier Administrator (Catalog Manager): An administrative user responsible for database maintenance and rule definitions. Utilizes a GUI for data entry but retains the ability to perform advanced manual rule manipulation and dataset transfers.
* Manufacturer (Technical Recipient): A passive system user who receives the finalized technical output (PDF) for production and assembly purposes.
2.4 Operating Environment
* Hardware: Android tablets, 10"+ display, ARM64 architecture.
* GPU Requirements: Minimum support for Vulkan 1.1+ for native rendering.
* OS: Android 11.0 (API Level 30) or newer.
* Connectivity: 100% Offline-First operation with optional HTTPS way for one-way catalog synchronization.
* Database: Local instance (SQLite) with encryption.


2.5 Design and Implementation Constraints
* Framework: Mandatory use of .NET MAUI for tablet-optimized layouts.
* Graphics API: The native Graphics Module shall utilize a modern API (Vulkan) via a C++17 plugin.
* Asset Format: 3D assets shall be provided in the .dae (Collada) format.
* Safety & Ethics: Categorized as Class B per IEC 62304. Patient data is strictly local and pseudonymized (GDPR).


2.6 User Documentation
* Instructions for Use (IFU): Mandatory guide for therapists (MDR Annex I).
* Technical Documentation: Documentation for administration and catalog updating (MDR Annex II).
* Software Release Record: Release notes and hardware/software environment requirements (IEC 62304).
* Context-Sensitive Help: Integrated tooltips providing real-time guidance based on risk management (ISO 14971).


2.7 Assumptions and Dependencies
* Asset Availability: The FDU team shall provide optimized 3D models in .dae format.
* Optional 3D Assets: The system shall function even if some components lack 3D models, providing appropriate UI warnings.
* Logic Accuracy: The FZS team shall verify the correctness of clinical and compatibility rules stored in the catalog.

4. Functional Requirements
4.1 FREQ-1: Clinical Assessment and Intake
* Description: Management of the patient assessment lifecycle.
* Priority: High
* Action Sequences:
   * FREQ-1.1: The system shall provide a structured checklist for ergonomic requirements, weight, and environmental usage.
   * FREQ-1.2: The system shall provide an initial "Recommended Assembly" based on validated intake data.
   * FREQ-1.3: The system shall prevent technical exports if mandatory intake fields are incomplete.
* Acceptance criteria: * Given a new session, when the therapist inputs patient weight and ergonomics, then the system updates the internal constraints (verifying FREQ-1.1 & FREQ-1.2).
   * Given an incomplete intake form, when the user attempts to export the BOM, then the system prevents the export and highlights missing fields (verifying FREQ-1.3).


4.2 FREQ-2: Validated Configuration Management
* Description: Real-time enforcement of technical and safety rules using JSON logic.
* Priority: High
* Action Sequences:
   * FREQ-2.1: The system shall perform deterministic cross-checks (mechanical, electrical, ergonomic) using structured rule definitions stored in the database.
   * FREQ-2.2: The system shall "lock" incompatible components and provide textual reasoning for selection rejections.
* Acceptance criteria:
   * Given a selected chassis, when the therapist selects an incompatible motor, then the system blocks the selection and displays a deterministic textual reason (verifying FREQ-2.1 & FREQ-2.2).
4.3 FREQ-3: Graphics Synthesis and Feedback
* Description: Visual confirmation via native rendering using Vulkan.
* Priority: High
* Action Sequences:
   * FREQ-3.1: The system shall pass PartIDs to a native rendering subsystem for off-screen processing.
   * FREQ-3.2: The system shall display the render (complete or partial) with clear warnings if 3D assets are missing.
* Acceptance criteria:
   * Given valid components with .dae files, when added to the configuration, then the native pipeline renders the assembly on-screen (verifying FREQ-3.1).
   * Given a selected component without a .dae file, when added, then the system displays the existing assembly with a clear "Incomplete Visuals" warning (verifying FREQ-3.2).


4.4 FREQ-4: Catalog and Rule Administration
* Description: Tools for managing component data and logic.
* Priority: Medium
* Action Sequences:
   * FREQ-4.1: The system shall provide a GUI for defining part parameters and mapping relationships visually.
   * FREQ-4.2: The system shall provide an "Advanced Mode" for direct manipulation and validation of structured rule definitions.
* Acceptance criteria:
   * Given Admin access, when the user opens the catalog manager, then they can edit parameters and JSON rules, and export the entire dataset (verifying FREQ-4.1 & FREQ-4.2).
________________


4.5 FREQ-5: Technical Output and Audit
* Description: Production-ready output and clinical traceability.
* Priority: High
* Action Sequences:
   * FREQ-5.1: The system shall utilize an internal document generation engine to create a technical Bill of Materials (BOM) including visual renders and part codes.
   * FREQ-5.2: The system shall record timestamps and TherapistIDs for audit purposes (IEC 62304).
* Acceptance criteria:
   * Given a completed valid configuration, when the user finalizes the session, then the system generates a PDF (using QuestPDF) containing the BOM, renders, and Therapist ID (verifying FREQ-5.1 & FREQ-5.2).


4.6 FREQ-6: Dataset Mobility and Provisioning
* Description: Data transfer and source management for the offline-first application.
* Priority: Low
* Action Sequences:
   * FREQ-6.1: The system shall support three methods of populating the catalog: Bundled Data, Sideloading (manual file import), and One-Way Sync (HTTPS).
   * FREQ-6.2: The system shall allow the export of complete local datasets (catalog + rules) into portable archives.
* Acceptance criteria:
   * Given a Wi-Fi connection, when triggered by an Admin, then the system performs a one-way sync of the catalog from the central HTTPS server (verifying FREQ-6.1).
   * Given an offline state, when provided with a valid database file, then the system successfully sideloads the catalog data (verifying FREQ-6.1 & FREQ-6.2).

* Primary Interface: A native Android application optimized for 10"+ tablets.
* Flow: Intake -> Part Selection with Validation -> 3D Visualization -> PDF Export.

5.2 Hardware Interfaces

* Storage: Read/write access for the local SQLite database, asset cache, and generated PDF documents.


5.3 Software Interfaces

* Format: Structured UTF-8 JSON files for rule exchange.
* Isolation: Strict isolation of patient data from network activities to comply with GDPR.

6. Other Nonfunctional Requirements
6.1 NFREQ-1: Performance Requirements
* Description: System performance, responsiveness, and speed metrics.
* Priority: High
* Action Sequences:
   * NFREQ-1.1: Visual preview updates shall not exceed 2.0 seconds after a component change.
   * NFREQ-1.2: Application cold startup time shall remain under 3.0 seconds.
   * NFREQ-1.3: PDF document generation shall be completed within 5.0 seconds.
* Acceptance criteria:
   * Given a component is changed, when the UI updates, then it must complete within 2.0 seconds (verifying NFREQ-1.1).
   * Given the application is launched from a cold state, when the home screen is displayed, then the elapsed time must be under 3.0 seconds (verifying NFREQ-1.2).
   * Given a finalized configuration, when the export is triggered, then the PDF generation must finish within 5.0 seconds (verifying NFREQ-1.3).


6.2 NFREQ-2: Safety Requirements
* Description: Enforcement of physical limits and fail-safe logic according to MDR and ISO 14971.
* Priority: High
* Action Sequences:
   * NFREQ-2.1: The system shall prevent a finalized state if the cumulative weight exceeds structural limits (MDR).
   * NFREQ-2.2: The rule engine shall implement fail-safe logic (unresolved or conflicting rules shall result in a safe "Restricted" state and specific part will not be selectable).
   * NFREQ-2.3: Safety-critical alerts shall use high-contrast visual elements complying with ISO 14971 risk management guidelines.
* Acceptance criteria:
   * Given an overweight assembly, when the user attempts to finalize, then the system blocks the action and shows a high-contrast alert (verifying NFREQ-2.1 & NFREQ-2.3).
   * Given a conflicting rule evaluation, when the engine processes it, then the system defaults to a "Restricted" state (verifying NFREQ-2.2).


6.3 NFREQ-3: Security Requirements
* Description: Protection of patient data and database encryption.
* Priority: High
* Action Sequences:
   * NFREQ-3.1: Patient data shall be pseudonymized and strictly isolated from any cloud synchronization processes (GDPR).
   * NFREQ-3.2: The local database and any export archives shall be encrypted using the AES-256 standard.
* Acceptance criteria:
   * Given a cloud sync event, when data is transmitted, then no patient-identifiable data is included in the payload (verifying NFREQ-3.1).
   * Given a saved local database or archive, when inspected, then the file contents must be encrypted with AES-256 (verifying NFREQ-3.2).


6.4 NFREQ-4: Software Quality Attributes
* Description: Maintainability of catalog data and reliability of the rule engine codebase.
* Priority: Medium
* Action Sequences:
   * NFREQ-4.1 (Maintainability): Catalog updates shall be possible via data updates (JSON/SQLite) without requiring recompilation of the application source code.
   * NFREQ-4.2 (Reliability): The codebase shall maintain at least 80% unit test coverage for the core Rule Engine logic to satisfy IEC 62304 criteria.
* Acceptance criteria:
   * Given a modified JSON/SQLite dataset, when loaded into the application, then the new rules apply without needing an app recompilation (verifying NFREQ-4.1).
   * Given the project test suite, when executed, then the code coverage report shows >= 80% for the Rule Engine module (verifying NFREQ-4.2).

7. System Design & Architecture
7.1 High-Level Architecture
  

The system follows a layered MVVM architecture built on .NET MAUI. The core application logic resides in C#, while the rendering is offloaded to a headless C++ Native library via P/Invoke.


7.2 Technology Stack
   * Frontend Framework: .NET 8 MAUI (C#).
   * Graphics Engine: Native C++17 plugin leveraging Vulkan SDK.
   * Database: SQLite + JSON1 extension for hybrid schema storage.
   * Document Generation: QuestPDF for deterministic PDF rendering.


7.3 Data Flow
   1. Input: Therapist inputs data via the MAUI UI.
   2. Query & Logic: The app queries the SQLite database and the JSON Rule Engine evaluates compatibility against the current assembly state.
   3. Rendering: If valid, Part IDs are sent via P/Invoke to the C++ Vulkan module. The module parses .dae files, renders the frame off-screen, and returns an image buffer to the UI.
   4. Output: Upon completion, QuestPDF compiles the data and images into a final BOM PDF.
8. Other Requirements
   * Internationalization: The system UI and database shall fully support UTF-8 encoding to correctly display and process the Czech language and special characters.
   * Legislation: Strict compliance with MDR (EU 2017/745), GDPR (EU 2016/679), and Czech Acts 375/2022 Sb. and 110/2019 Sb.
   * Risk Management: Development processes and safety-critical features must comply with ISO 14971.
